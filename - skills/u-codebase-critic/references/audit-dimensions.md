# Codebase Critic Audit Dimensions

This reference defines the exact scope of each specialist pass. Use the definitions to increase recall without manufacturing duplicate findings.

## Operating rules

- A dimension name is not a finding. Require a concrete observed failure, affected path, present or credible future impact, and durable direction.
- Scan the complete inventory for the assigned concern, then read every plausible hit and enough neighboring source to prove or refute it.
- Keep one primary dimension per candidate. Add related dimensions as tags; do not restate the same root cause as several findings.
- Coverage lenses identify where scrutiny must occur. Size, churn, public exposure, shared use, or security sensitivity alone is not a defect.
- Use the bundled references only. `Coding` means `coding-guide.md`; `AI` means `vibecoding-blunder-prevention-guide.md`.
- Locate routed sections by their headings, not fixed line numbers.

## Candidate ownership rules

When several dimensions observe the same root cause, choose the dimension that most precisely names the failure:

- Prefer D08/D09/D14 for concrete security, privacy, or correctness harm over generic D25 boundary weakness.
- Prefer D17 for parallel end-to-end systems, D18 for divergent one-off primitives, and D05 for repeated local logic.
- Prefer D06 for unreachable code, D19 for superseded but still-living code, and D32 for abandoned prototype residue.
- Prefer D16 for an explicit current-intent contradiction and D07 for misleading historical residue.
- Prefer D21 for responsibility placement, D02 for repository/module shape, and D31 only as a hotspot tag.
- Prefer the underlying failure dimension over D13, D22, D23, D27, D28, D30, or D31 when those dimensions merely located the problem.

The main critic may change a candidate's primary dimension during canonical synthesis, but it must preserve all contributing reviewer and dimension provenance.
